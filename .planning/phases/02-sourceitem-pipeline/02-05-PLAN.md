## Planner decisions recorded for this plan

- **Located diagnostics as data.** A per-record diagnostic becomes `RecordDiagnostic { topic: String, offset: i64, message: String }`. Two `Incoming` variants carry it: `Skipped` (the record gives no output record) and `Note` (the record is still written; the note is a warning about it). The collector never parses message text to find an offset. The `message` keeps its current wording, so every kept line reads exactly as before.
- **Two range sets per topic.** Past the cap, a `Skipped` offset goes into the topic's `skipped` ranges and a `Note` offset into its `noted` ranges. Mixing them would let a range span a written record, which the user ruled out ("Ranges are allowed only when exact"). Notes are named too, not only counted: a social record's note can arrive just before a stop (limit or budget) that leaves its record unread, and naming the note's offset keeps even that record named.
- **Exactness rule.** `OffsetRanges::add` extends the last range only when the new offset equals its end plus one, using a checked add. An offset already inside the last range (a second note on one record) changes only the count. Anything else starts a new range. Fluvio offsets in one partition are consecutive integers and each branch delivers its topic in offset order, so this rule merges a flood into one range and never spans an offset that was not added. Out-of-order offsets would only start more ranges, never a wrong one.
- **Memory and work bounds.** `diagnostic_budget` and `finish_batch` stay byte-identical to commit 98e70f6. `MAX_DIAGNOSTICS` still caps kept messages. A suppressed record costs at most one `(i64, i64)` range entry and nothing when it extends the previous range; its topic is stored once per topic as the map key. The number of suppressed records is bounded by `diagnostic_budget(limit)`. The message string of a suppressed record is built by its producer, as today, and dropped by the collector without being kept.
- **Line format (stderr text, not a contract).** Per topic, in topic-name order (`BTreeMap`): `{topic}: {n} more skipped record(s), details not shown, offsets {ranges}`, then `{topic}: {n} more record diagnostic(s), details not shown, offsets {ranges}`, each only when its count is non-zero. `{n}` is the range set's count; `{ranges}` is its `Display`. README.md and `.planning/codebase/*.md` quote no consume diagnostic (checked at plan time), so the old count-only closing line can go.
- **Tracer staging.** Task 1 adds the new types and routes only the social parse-failure path through them, end to end, while the other producers keep the old string-only variant for one commit. Task 2 moves every other producer, deletes the string-only variant and the count field, and adds the noted ranges.
