<objective>
Make the provider refresh. When a poll is about to run and the access token has under 60 seconds left, refresh it first (under the per-alias lock, after re-reading the file), persist the new login atomically, and hand the guest the new access token; on failure apply D-09 exactly. Wire the outcomes into the scheduler and into `fili plugins run-once`.

Purpose: AUTH-02 (the user never has to log in again during normal polling), the rest of D-07, D-08 and D-09, and D-15. This replaces plan 06-01's refresh seam with the real thing.

Output: the refresh path in `provider.rs`, the scheduler and run-once mapping of its outcomes, and the tests.

Flagged assumptions (edge probe; the user has not ruled): the provider call is not raced against shutdown (a stop must not cut a refresh between the provider's answer and the file write), so a stop can wait up to the client's 30-second timeout and the supervisor's 10-second grace may abort it; with a provider that rotates refresh tokens a crash between the network answer and the file write can lose the only valid refresh token, which is inherent to rotation and is documented in plan 06-09's README (RESEARCH Pitfall 4). The refresh holds the per-alias lock across the network call, so a login started during a refresh waits for it, up to the lock's 30-second wait.
</objective>
