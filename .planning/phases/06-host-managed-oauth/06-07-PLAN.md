<objective>
Deliver `fili auth login <plugin>`: the user runs it once, approves in the browser, and the host stores a login the poll loop then keeps fresh.

Purpose: AUTH-01 through D-05 (print the URL and also open the browser; `--no-browser` suppresses the launch; works over SSH), D-06 (nothing written on failure) and D-14 (the `authorize_params` reach the authorize URL). The flow itself lives in `src/plugins/auth/login.rs` behind a small hooks trait so tests drive it end to end against a fake token endpoint with no browser; `src/commands/auth.rs` supplies the real hooks (print, open the browser) and the registry and config lookup.

Output: `login.rs`, `commands/auth.rs` with the login command, the `Auth` subcommand wiring in `cli.rs`, `main.rs` and `commands/mod.rs`, the `open` dependency, and the tests. Plan 06-08 adds `status` and `logout` to the same command module.

Flagged assumptions (edge probe; the user has not ruled): `fili auth login` for a plugin that already has a login simply replaces it after a successful exchange (no confirmation prompt); a login that returns no refresh token is stored and reported, not refused (some providers need `authorize_params`); a running `fili run` can lag behind a fresh login by up to the plugin's backoff window (RESEARCH Pitfall 8), which the success message says; Ctrl-C during the wait ends the process with nothing written, because the write comes only after the exchange.
</objective>
