<objective>
Prove, on real wasm components, the first two roadmap success criteria, and give `fili plugins run-once` the same routing as `fili run`. A source's requests go to the fetcher the registry assigns and nowhere else; changing the assignment changes who serves them without rebuilding anything; and the allowlist and the timeout hold whichever fetcher is in charge, the default one or a custom one. A custom fetcher is simulated by extending the existing stub fetcher with test-only behaviours.

Purpose: FETCH-01 (calls routed to the configured fetcher, swappable by configuration alone) and FETCH-02 (allowlist and timeout enforced regardless of which fetcher handles the request), including the concurrency edge.

Output: wasm tests, two backward-compatible fixture extensions (rebuilt), a single-source route builder in `loader.rs`, and `run_once` routing.

Working decisions (no CONTEXT.md; the user may override before execution):
- WD-18 The stub fetcher doubles as the "custom fetcher" and is driven by a request header, `x-stub-mode`: `spin` loops forever, `forward:<url>` calls `outbound-http.send` for that url and returns its result unchanged, and any other request gets the canned 200 as before. A header keeps the registry and the component unchanged between tests. The stub source gains an optional `fetch_headers` table so a test can set that header.
- WD-19 In `run-once` the fetcher is loaded before the source's own component, so a broken dependency is reported first and by name; a dry run still creates nothing.

Flagged assumptions (edge probe, the user has not ruled): FETCH-02 concurrency is resolved here as the per-call deadline and the surviving-route truths. The ordering and request-validation edges are plan 05-04; the TLS proof is plan 05-05.
</objective>
