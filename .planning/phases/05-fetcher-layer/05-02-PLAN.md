<objective>
Ship the default HTTP fetcher component (`plugins/http-fetcher`): a minimal `fetcher`-world plugin whose `fetch` forwards the request to the host's `outbound-http.send` and returns the answer. It is a normal registry entry (`[fetchers.http]`), built with `cargo component` like the other plugin crates and registered in the sample registry.

Purpose: FETCH-03 (filimon ships a default HTTP fetcher component). The component is deliberately thin: all network behaviour, TLS certificate validation, redirects, size caps and the allowlist live in the host's `send` (plans 05-03 and 05-04), so every fetcher, default or custom, is held to the same rules and a guest cannot weaken them.

Output: the new crate, a README entry and the sample registry path.

Working decisions (no CONTEXT.md; the user may override before execution):
- WD-07 The default fetcher is a component listed in the registry, not embedded in the `fili` binary. Embedding would make an unlisted component run, which HOST-01 forbids. "Ships" means the source crate is in the repository, builds with one documented command, and the sample registry points at the result.
- WD-08 The guest is a pure pass-through. It does not follow redirects, set headers or retry: the host's `send` follows redirects (each hop re-checked against the allowlist, plan 05-03) because the `url` crate and the allowlist already live there.

Flagged assumptions (edge probe: FETCH-03 is `unclassified`, the user has not ruled): which certificate authorities are trusted is the host client's setting, not this component's. Plan 05-03 uses the roots bundled with the HTTP client, so a TLS-intercepting corporate proxy CA is not trusted. This is documented in plan 05-08.
</objective>
