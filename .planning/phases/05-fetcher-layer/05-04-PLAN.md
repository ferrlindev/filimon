<objective>
Finish the host's request rules so that the policy a guest meets is complete: refuse requests that could defeat the allowlist or smuggle framing (a `host` header, framing and hop-by-hop headers, malformed headers, oversized requests), keep the header and body round trip faithful, and prove the host's own logs never carry secrets.

Purpose: FETCH-02 (the host, not the fetcher, decides what a request may be). Plan 05-01 added the url rules and plan 05-03 the network behaviour; this plan completes `FetchPolicy::check` for the parts of a request that are not the url. The check runs both when a source calls `fetch` and when a fetcher calls `send`, so one rule holds at both.

Output: validation in `fetch.rs`, a small helper in `testing.rs`, and the tests.

Working decisions (no CONTEXT.md; the user may override before execution):
- WD-13 The forbidden request headers are fixed: `host`, `content-length`, `transfer-encoding`, `connection`, `proxy-connection`, `upgrade`, `te`, `trailer`. The HTTP client owns message framing and the connection; a guest that sets them could confuse framing or choose the virtual host.
- WD-14 Limits: at most 100 request headers, 64 KiB of header names and values in total, a 1 MiB request body (`MAX_REQUEST_BODY_BYTES`) and an 8 KiB url. They are fixed constants, like the memory and item caps from Phase 3.
- WD-15 Cross-name header order is unspecified and documented as such; only the order of repeated names is a guarantee, because the HTTP client's header map groups by name.

Flagged assumptions (edge probe, the user has not ruled): FETCH-02 ordering is resolved as the same-name guarantee above. This plan is a hardening slice of the routing path that plans 05-01 and 05-03 prove end to end, so it has no tracer task of its own.
</objective>
